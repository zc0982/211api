# Go 工具链与安全验证

- Go 标准库安全修复必须同时更新 `backend/go.mod`、三个 Dockerfile 和 backend-ci/release/security-scan workflow 的版本断言；仅更新测试环境不能保证发行镜像包含修复。
- `deploy/tests/release-delivery-integrity-test.sh` 以 go.mod 为基线验证上述构建入口一致。
- 本地和 CI 均运行 `make -C backend test-security`：临时安装最新 govulncheck，输出实际 Go、扫描器和漏洞库时间，再扫描全部后端包。扫描失败须保留原始退出码，不增加漏洞豁免。
- 本地与 CI 结果不一致时，以相同 head 的失败日志定位具体漏洞，并核对工具链、扫描器和漏洞库版本。升级扫描器不保证所访问的漏洞库索引已经包含新条目。
- 可用官方 OSV 条目构造临时定向扫描，验证旧工具链失败、新工具链通过；单条漏洞验证不代替完整安全扫描，也不得替换 CI 默认漏洞库。
- 仅在最新 head 的 CI 安全扫描成功后，才能宣称该 PR 的安全门禁通过；旧 head 或本地旧索引的成功不能替代。
- 升级工具链后重跑单测、集成测试、竞态检测与发行构建。读取进程级内存指标的回归用例应在独立进程测量，保留业务断言和原有上限，避免其他用例的后台活动污染测量；不能以放宽阈值或重复执行替代修复。
